# TUDa-HWAI GitHub 仓库管理规范

**语言：[English](./REPOSITORY_POLICY.md) | 简体中文**

**Hardware for Artificial Intelligence（HWAI）**  
**德国达姆施塔特工业大学（TU Darmstadt）**

**版本：** v1.0
**适用范围：** `TUDa-HWAI` GitHub Organization 下的所有代码仓库。

---

## 1. 总体原则

TUDa-HWAI GitHub Organization 是 HWAI 研究组用于托管、发布和长期维护科研软件及代码的官方平台。

所有代码仓库应遵循以下原则：

- **专业性（Professionalism）：** 仓库应具有清晰的名称、完整的文档以及规范的目录结构。
- **可复现性（Reproducibility）：** 已发表研究成果的代码应支持其他研究人员独立复现论文中的方法和实验结果。
- **透明性（Transparency）：** 科研成果应得到准确描述，明确标注相关论文、作者及引用信息。
- **安全性（Security）：** 不得公开敏感信息、保密数据、账号密码或访问凭据。
- **长期维护性（Long-term Maintenance）：** 即使原项目成员毕业或离开研究组，相关科研代码也应保持可访问、可使用和可维护。

## 2. 仓库创建与审批

### 2.1 仓库归属与责任

- 所有 HWAI 官方科研代码仓库必须创建在 `TUDa-HWAI` Organization 下。
- 每个仓库必须指定至少一名**仓库负责人（Repository Maintainer）**，负责代码内容、文档及日常维护。
- 至少还应有一名 HWAI 成员具备足够的仓库访问权限，以便主要负责人无法继续维护时进行交接。
- Organization Owner 权限仅授予经过授权的研究组管理人员。

### 2.2 仓库创建审批

创建新的官方仓库前，研究人员应获得课题组负责人（PI）或被授权的 Organization Owner 的批准。

申请应包含以下信息：

- 拟创建的仓库名称
- 对应项目或论文标题
- 项目负责人及主要参与人员
- 仓库可见性：Private 或 Public
- 论文发表或项目发布状态
- 拟采用的软件开源许可证

### 2.3 仓库命名规范

仓库名称应当简洁、明确、具有辨识度，并尽可能长期保持稳定。

推荐示例：

- `Basis_Sharing`
- `CompressKV`
- `NN2Logic`
- `DiffLUT-Network`

不推荐使用：

- 临时性名称，如 `test123`、`new-project`、`final-code`
- 与研究项目无关的个人姓名
- 可能误导他人认为论文已经被某会议录用的名称
- 公开发布后频繁更改仓库名称

已经被论文引用的仓库应尽量保持原名称，避免影响已发表论文中的代码链接。

## 3. 仓库可见性与公开发布

### 3.1 私有仓库（Private Repositories）

- 新研究项目原则上应先创建为 Private 仓库。
- 对于正在投稿或审稿中的论文，应遵守相应会议的匿名审稿及代码公开政策。
- 未发表、涉密或受到合作协议限制的研究成果，未经授权不得公开。

### 3.2 公开仓库（Public Repositories）

将仓库从 Private 修改为 Public 前，必须：

1. 获得 PI 或指定负责人的批准。
2. 确认代码、数据集、模型权重及相关依赖具有合法的公开发布权限。
3. 检查整个 Git 历史，确保不存在敏感信息、密码和访问凭据。
4. 完成仓库所要求的文档和说明。
5. 验证代码及安装步骤能够正常运行。
6. 确认公开发布不违反会议、学校、合作协议、知识产权或其他相关规定。

**禁止对论文的录用及发表状态进行不准确或误导性的标注。**

## 4. 仓库基本信息规范

每个公开科研仓库必须完善以下信息。

### 4.1 Description（仓库简介）

对于已经录用或发表的论文，统一采用：

`[Venue Year] Official Paper Title`

例如：

`[AICAS 2024] Early-Exit with Class Exclusion for Efficient Inference of Neural Networks`

对于尚未正式录用的论文，直接使用论文或项目标题，不添加未经确认的会议名称。

### 4.2 Website（项目网站）

应填写最合适的正式资源链接，包括：

- 正式发表论文的 DOI 或出版社页面
- OpenReview 论文页面
- arXiv 预印本页面
- 官方项目网站

### 4.3 Topics（技术标签）

每个仓库建议设置 4–6 个与项目技术内容相关的 GitHub Topics。

例如：

`large-language-models`、`model-compression`、`fpga`、`hardware-acceleration`、`efficient-inference`、`neural-networks`

Topics 应准确反映项目的技术贡献，避免添加无关关键词。

## 5. 仓库文件与文档要求

每个公开科研仓库应根据项目实际情况包含以下文件：

| 文件 | 用途 |
|---|---|
| `README.md` | 项目介绍、环境安装、使用说明及实验复现 |
| `LICENSE` | 代码使用、修改和再分发的法律授权 |
| `CITATION.cff` | 软件及对应论文的引用信息 |
| `requirements.txt`、`environment.yml` 或等效文件 | 项目依赖和环境配置 |
| `.gitignore` | 排除临时文件、生成文件及敏感配置 |

推荐增加以下文件：

| 文件 | 用途 |
|---|---|
| `CONTRIBUTING.md` | 外部贡献与代码审查规范 |
| `SECURITY.md` | 安全问题报告政策 |
| `CHANGELOG.md` | 记录重要版本变化 |
| `.github/workflows/` | 自动化测试和代码质量检查 |
| `examples/` | 最小可运行示例 |
| `configs/` | 实验配置文件 |

### 5.1 README 必须包含的内容

1. 项目名称及简要介绍
2. 论文标题、作者和发表信息（如适用）
3. 安装方法及依赖环境
4. 数据集获取及预处理方法
5. 训练、评估或推理命令
6. 预期输出或代表性实验结果
7. 硬件及软件环境要求
8. 论文引用方式
9. 开源许可证及问题反馈渠道

如果部分实验无法使用公开资源复现，必须在 README 中明确说明相关限制。

## 6. 科研实验可复现性

科研代码仓库应提供足够的信息，使外部研究人员能够理解、运行和评估相关工作。

对于机器学习研究项目，应尽可能包含：

- 模型架构及实现细节
- 数据集名称、来源、版本和预处理方式
- 训练与评估配置
- 随机种子及相关复现设置
- 软件框架和依赖库版本
- CUDA、GPU、FPGA 或其他硬件环境要求
- 复现主要实验的运行命令
- 预期实验指标及已知误差或限制

大型数据集、模型权重和生成的实验文件应通过适当的存储平台发布，不应直接提交到普通 Git 仓库。

如果完整训练所需的计算资源过高，仓库负责人至少应提供经过测试的最小运行示例，并说明完整复现实验所需的资源。

## 7. 论文引用与开源许可

### 7.1 论文引用（Citation）

所有与科研论文相关的代码仓库必须包含有效的 `CITATION.cff` 文件。

要求如下：

- 已录用论文应使用经过核实的正式录用信息。
- 已发表论文应优先使用官方 DOI（如有）。
- 未正式录用的论文不得标注未经确认的会议或期刊。
- 论文正式发表后，应及时更新推荐引用信息。
- 必须核对作者姓名、作者顺序、论文标题以及发表标识。

### 7.2 开源许可证（Licensing）

每个公开发布的代码仓库都必须具有经过批准的明确开源许可证。

- 许可证必须符合学校、资助方、合作项目及第三方代码的相关要求。
- 仓库负责人在选择或修改许可证前，必须获得相应授权。
- 使用第三方代码时，必须保留其要求的版权声明和署名信息。
- 模型权重和数据集可能需要与代码不同的使用许可。

**代码公开可见并不代表他人可以不受限制地使用、修改或重新分发。**

## 8. 代码开发与审查规范

### 8.1 分支管理（Branch Management）

- `main` 作为稳定的默认分支。
- 新功能和非简单错误修复应在独立分支中开发。
- 重要代码变更应通过 Pull Request 提交。
- 应限制对受保护分支的直接 Push。
- 未经特别授权，不得强制 Push 或删除受保护分支。

### 8.2 Pull Request 审查

对于重要代码变更：

- 至少需要一名获得授权的审查人员批准。
- 合并前应完成必要的测试。
- Pull Request 应说明修改目的和潜在影响。
- 对已经发表论文实验结果产生影响的更新，应由相关项目负责人进一步审查。

### 8.3 Commit 规范

Commit message 应简洁、准确地描述修改内容。

推荐示例：

- `Add training scripts for ImageNet experiments`
- `Fix attention mask in inference pipeline`
- `Update README with evaluation instructions`
- `Add citation metadata for accepted paper`

不建议使用 `update`、`fix`、`final version` 等缺乏具体信息的 Commit message。

## 9. 安全与访问权限

- Organization 成员和仓库权限应遵循**最小权限原则（Principle of Least Privilege）**。
- 管理权限仅授予获得授权的负责人。
- 建议所有贡献者启用双重身份验证（2FA），并在完成组织成员的准备检查后实施强制 2FA。
- 严禁在仓库中提交 API Key、密码、Access Token、SSH 私钥、个人敏感信息以及保密数据。
- 敏感凭据必须通过经过批准的 Secrets 管理机制保存。
- 如果意外泄露凭据，必须立即报告并撤销或轮换受影响的凭据。
- 仓库删除、所有权转移和 Public/Private 状态修改必须获得 Organization Owner 的明确批准。

外部贡献和自动化工作流必须按照项目的安全要求进行审查。

## 10. 论文代码发布与版本管理

正式发布论文代码时：

1. 创建对应的 GitHub Release。
2. 标明相关论文版本或发表状态。
3. 简要说明该版本支持复现的实验。
4. 创建稳定的版本标签，例如 `v1.0.0` 或 `paper-release-v1`。
5. 尽可能保留论文发表时的正式代码版本。

后续重要修改应记录在版本说明中。

即使仓库持续更新，也必须能够追溯到论文最初使用的实验实现版本。

## 11. 仓库维护与归档

### 11.1 活跃项目维护

每个活跃仓库必须指定明确的负责人。

仓库负责人应：

- 在合理范围内及时回应相关 Issues。
- 确保文档内容与实际代码保持一致。
- 检查安全问题和依赖库风险。
- 必要时更新实验复现说明。

### 11.2 研究人员毕业或离组

研究人员离开 HWAI 前，应完成以下工作：

- 移交仓库管理职责。
- 整理未解决的问题及重要配置。
- 确保研究组能够访问所需的代码、文档和获准保留的研究成果。
- 撤销不再需要的仓库访问权限。

### 11.3 不再维护的项目

经批准后，不再维护的仓库可以设置为 Archive 状态。

已经发表论文对应的公开仓库原则上应长期保留，以保障学术成果的可复现性。

删除、重命名或转移已经发表论文的仓库前，必须明确评估对论文引用和已有链接的影响。

## 12. 规范执行与例外情况

每个仓库负责人都有责任确保其项目遵守本管理规范。

在具有合理理由的情况下，PI 或其授权的 Organization Owner 可以批准有记录的例外情况，例如：

- 科研保密要求
- 论文发表与审稿政策
- 知识产权限制
- 信息安全要求
- 项目特定的技术限制

任何例外均不得危及 Organization 的安全，也不得造成对已发表科研成果的不准确描述。

## 附录：新仓库公开发布检查清单

在将仓库设置为 Public 之前，必须检查以下事项：

- [ ] 仓库名称和 Description 准确、规范。
- [ ] 已获得 PI 或指定负责人的发布批准。
- [ ] 已检查论文发表及知识产权相关限制。
- [ ] README 包含正确、可执行的安装及使用说明。
- [ ] 已记录软件依赖及环境版本。
- [ ] 已测试主要实验或最小运行示例。
- [ ] 论文信息和 `CITATION.cff` 准确。
- [ ] 已确认开源许可证及第三方代码署名要求。
- [ ] 仓库中不存在密码、Token、敏感信息或禁止公开的数据。
- [ ] 已指定至少一名仓库负责人。
- [ ] 已配置适当的仓库权限及分支保护。
- [ ] 在适用情况下，已准备正式发布版本或 Git Tag。

**只有在完成必要检查并获得批准后，科研代码仓库才能正式公开发布。**
